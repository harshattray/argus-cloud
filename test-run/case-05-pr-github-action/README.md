## The first run went red, and it was not a regression

The initial CI run failed in 14s with "1 failing check". Two bugs, both in
this workflow, neither in Normascope's scoring:

1. **The install crashed before Normascope ran.** `npm install norma-scope`
   died with ERESOLVE because the package pins `@anthropic-ai/sdk` to
   `^0.112.3` as an optional peer and this repo uses `^0.115.0`. That is a
   real shipped bug — see
   [finding-peer-dependency-install](../finding-peer-dependency-install/).
   Fixed here by installing into a scratch prefix.
2. **Pass 1 used the wrong config.** It checked out the base branch and
   captured with the *base's* `.bridge/config.json`, which still tracks the
   old three full-page frames. The baselines landed under frame names the
   head never asks for, so every frame in pass 2 would have skipped as "no
   approved baseline". Pass 1 now checks out the head's config over the base
   source.

**A red check is the wrong signal for a flagged frame.** Normascope is
non-blocking: `check --json` exits 0 whatever the scores are, and only
`--strict` exits 1. A visual regression should surface as the sticky comment
and nothing else. This job goes red only on genuine infrastructure failure.
Worth saying so explicitly in the Action's README — "the check is red because
CI broke" and "the check is red because your UI changed" are different
signals and users will conflate them.

## The cross-platform problem, and why this workflow is not the stock Action

This is the part worth writing up properly, because it bites everyone doing
visual regression in CI.

Committed baseline PNGs get captured wherever `norma-scope baseline` ran —
in practice a developer's macOS laptop. CI runs `ubuntu-latest`, which
rasterises text through an entirely different stack. Diffing a macOS baseline
against a Linux capture produces enormous mismatch percentages that have
nothing to do with the change under review, and the report becomes noise.

`normascope.yml` here **never uses the committed baselines**. It runs two
passes in one runner:

1. check out the **base** sha → build → serve → `auto` → `baseline`
   → copy `.bridge/baseline` to `$RUNNER_TEMP`
2. check out the **head** sha → build → serve → restore that baseline
   → `check --json`

Both images come from identical hardware, OS, browser and fonts, so every
pixel of difference is attributable to the diff under review. The committed
baselines stay useful for local pre-commit runs.

The stock composite Action in `action.yml` does not do this — it captures once
and diffs against whatever baseline is in the repo. For fidelity mode against
a committed Figma snapshot that is fine, since the reference is a design
export rather than a browser capture. For **baseline mode across platforms it
is not**, and the Action's README should say so. This two-pass workflow is a
candidate to fold back into `action.yml` as an option.

## Other things this shook out

**`/articles` had to be dropped** from the tracked frames. It renders from the
API, and `vite preview` does not apply the dev server's `/api` proxy, so it
renders differently in CI than in local dev — it measured 0.8% against a
dev-server baseline purely from missing data. A frame that depends on a
backend the CI job does not run is not a reproducible frame.

**The production build renders identically to the dev server** for all six
remaining frames — 0.00% across the board. Worth knowing: you can capture
baselines from `vite dev` and compare against a `vite preview` build without
introducing drift.
